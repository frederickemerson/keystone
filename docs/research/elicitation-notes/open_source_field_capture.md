# Open-source field / frontline capture: patterns Keystone can adopt

Scope note (12 Oct 2026). I verified every repository with `gh api repos/OWNER/REPO`, which gave the star count, the last push date (`pushed_at`) and the SPDX licence. Where GitHub reported "NOASSERTION", I read the licence file itself. Traction and reception figures come from web search, and most are self-reported by the project or vendor. I ran DeepWiki (`npx @seflless/deepwiki ask`) on 8 repositories: ODK Collect, RapidPro, Glific, CHT Core, CommCare HQ, Atlas CMMS, Ushahidi and KoboToolbox KPI. DeepWiki answers are generated from the code by AI. I spot-checked one claim in the code: Atlas CMMS voice notes, confirmed with `gh search code`. In the current Keystone code, `app/` has no `MediaRecorder`, `getUserMedia` or `SpeechRecognition` usage, and the expert side of `/capture` is scripted. Every live-capture idea below is therefore new work.

## 2. Cross-cutting capture patterns (what the successful ones share)

### Takeaway
The platforms that scaled to millions of frontline workers (ODK/Kobo, CommCare, CHT, RapidPro) do not ask workers to write knowledge. They (a) attach capture to an event or case that already exists, (b) **preload context** so the worker answers only the delta, (c) **never block** on connectivity or structure, and (d) put structuring and verification on a different person, at a different time, with a visible status. Newer projects (Kobo 2025–26, Glific) now insert ASR plus an LLM between raw voice and structured fields, while keeping the raw input and a human review status.

### Cited findings
- Offline-first with a local store and retry or auto-send is universal. ODK sets an instance status of COMPLETE or SUBMISSION_FAILED and auto-sends from a scheduler. CHT uses PouchDB↔CouchDB. CommCare uses incremental OTA restore (DeepWiki on each repo).
- Context preload and follow-up: ODK Entities ([docs](https://docs.getodk.org/entities-intro/)), CommCare `PreloadAction` and `UpdateCaseAction`, and CHT task emission from rules.
- Capture first, structure later: Ushahidi `draft` posts. Field Papers paper-to-scan. Haiti 2010 needed volunteers to translate and geolocate ~40k messages ([Wikipedia](https://en.wikipedia.org/wiki/Ushahidi)).
- AI with provenance and review: Kobo stores `engine` and `revisions` and marks AI vs manual in exports ([KoboToolbox blog](https://kobotoolbox.org/blog/improving-qualitative-data-collection-kobotoolboxs-advanced-features-for-transcription-translation-and-analysis); Kobo staff on the [forum](https://community.kobotoolbox.org/t/may-2026-feature-update/76236) say transcription uses Google STT v2 and analysis uses gpt-oss-120b).
- Chat-native voice: Glific runs voice note → STT (Bhashini or Google) → `parse_via_chat_gpt` with a field list, plus GPT-vision on photos (DeepWiki, glific/glific).
- IVR: RapidPro has `wait_recording` and `wait_digits` nodes in the same flow JSON as its chat flows (DeepWiki, rapidpro/rapidpro).
- CMMS: Atlas CMMS has an audio recorder on work orders and requests (verified file paths above).

### Inferences
- For Keystone, these patterns translate to: *bind capture to the work order (event) and the asset or pill (case). Preload the rule's triggers and evidence. Ask only for the gap. Accept raw voice or photo. Let the LLM draft a rule tile with an `engine` and provenance stamp. Route it to the expert or steward to confirm, using the existing Draft→Shadow→Approved status.*
- Keystone's differentiator against all of these: they capture **observations or data**, while Keystone captures **decision rules**. None of the projects surveyed turns field input into a versioned, deterministic decision rule. That is the pitch line.

### Gaps
- DeepWiki answers are AI summaries. Only Atlas voice notes were confirmed in code.
- I found no adoption figures for DHIS2 in this pass. The Glific NGO count (100+) comes from a single, possibly dated, article.
- I found no open-source after-action review or lessons-learned tool with real traction.
- I have not verified MERaLiON's licence terms for commercial or hackathon use (MERaLiON Public License). Read it before demoing.

### Recommended hackathon cut (about 16–20 h)
Do #1, #3 and #6, with #4 if time allows. Together they make one demo beat: *the tech scans the QR on the AHU → records 10 seconds after overriding gate TS-07 → a draft tile appears on the Chief Engineer's canvas with an audio quote → he confirms → v1.3*. This extends Wow 2 ("how does it get smarter?") with frontline-sourced evidence. All of it uses MIT or BSD pieces or code we already have, so there are no AGPL obligations.

### Inferences / risks
- AGPL projects (Glific, RapidPro, CHT, Kobo KPI, Atlas) are best used as **design references**, not embedded, unless Keystone is willing to open its source. Courier is now BSL-1.1.
- Plant-room noise and PPE argue for capture after the job, and for hold-to-talk over ambient recording (see `frontline_singapore.md` §1).
- WhatsApp requires the Business API and template approval. Telegram is faster for a demo. Either way, state the PDPA data-governance caveat.
